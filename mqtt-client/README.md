# mqtt-client（マイコン役）

[`rumqttc`](https://crates.io/crates/rumqttc) を使った、「マイコン役」専用のMQTTクライアントです。
`mqtt-server`（パソコン役：ブローカー＋指示出しロジックが同居）プロジェクトとは独立しており、
単独でビルド・実行できます（接続先のMQTTブローカーは別途必要です）。

以前はこのプロジェクト1つでパソコン役・マイコン役の両方を`listen_port`引数の有無で切り替えて
いましたが、パソコン役のロジックは`mqtt-server`側に移したため、今はマイコン役専用になっています。

## 使い方

```sh
cargo run -- <名前> <listen_port> [host] [port] [topic]

# 例
cargo run -- device1 9101 127.0.0.1 1883 chat
cargo run -- device2 9102 127.0.0.1 1883 chat
```

`<名前>`と`<listen_port>`は必須、`host`・`port`・`topic`は省略可能で、それぞれ`127.0.0.1`/`1883`/`chat`
がデフォルトです。マイコン役は必ずファイル受信用のTCP待ち受けを行うため、`listen_port`は省略できません。

起動すると、ブローカーへ接続してすぐに以下を行います。

- `<topic>/presence/<名前>` へ`retain=true`で`{"status": "online", "seq": 0}`をpublish（在室通知）
- 異常切断時に自動配信されるLast Willとして、同じトピックへの`{"status": "offline", ...}`を登録
- 指定した`listen_port`でTCPの待ち受けを開始（パソコン役からのファイルを受け取るため）

行を入力してEnterを押すと`<名前>: <入力内容>`が`<topic>`にチャットとしてpublishされます
（デバッグ用の簡易機能。`Ctrl+D`で送信スレッドを終了できます）。

## ファイル受信

パソコン役（`mqtt-server`）から`/send`でファイルを送られると、以下の流れで受信します。

1. 自分専用のトピック`<topic>/file/offer/<自分の名前>`へ届いたOFFERに反応する
2. 「ここに繋いで」という返事（自分の現在のIPアドレス＋固定listen_port）を
   `<topic>/file/ack/<申し出てきたパソコンの名前>` トピックへpublish
   （IPアドレスはDHCPで変わることがあるため、返事のたびに毎回調べ直しています）
3. パソコン役がそのアドレスへ直接TCP接続してくるので、`id`＋ファイル名＋サイズ＋中身の順に受け取る
4. 受信が終わった（または途中で失敗した）ら、結果を`<topic>/file/received/<自分の名前>`トピックへ
   `{"id": "...", "who": "device1", "status": "ok", "size": 12345, "seq": 4}`としてpublishする

MQTTは大きなバイナリデータの配信には向いていないため、**ファイルの中身そのものはMQTTに乗せず、
別途つないだ生のTCPソケットで直接送受信**する方式にしています。自分のIPアドレスは「ブローカーに
疑似接続してみて使われるローカルアドレスを覗く」という方法で自動検出しています（同一LAN内での
利用を想定した簡易実装で、インターネット越しやNAT環境ではそのままでは動きません）。

## ジョブの実行

パソコン役から`<topic>/job/queue`へ一斉配信されるジョブ（`{"id", "from", "content", "seq"}`）を
受け取ると、内容を表示して処理を行い（このサンプルでは実際の印刷は行わず、1秒待つだけのダミー処理）、
完了したら`<topic>/job/done/<自分の名前>`へ完了報告をpublishします。実機では、この「1秒待つ」部分を
実際の印刷やモーター制御などの処理に置き換えることになります。

## プロジェクトの中身

- `src/main.rs` — 起動処理・トピックの組み立て・OFFER/JOB受信時の処理・メインループ
- `src/file_transfer.rs` — 生TCPでのファイル受信ロジック（`run_file_listener`など）と、自分のIP自動検出
- `src/messages.rs` — MQTTでやり取りするメッセージの形（JSON、`mqtt-server`の同名ファイルと同じ内容）
- `src/seq.rs` — メッセージ欠落検知用のseq番号の仕組み（`mqtt-server`の同名ファイルと考え方は同じ）

`messages.rs`と`seq.rs`は`mqtt-server`側にも同じ内容のファイルがあります。2つのプロジェクトは
意図的に別々のCargoクレート（共有ライブラリなし）にしているため、通信フォーマットを変えるときは
両方のファイルを一緒に直す必要があります。

## トピック構造とseq番号（Sparkplug Bを参考に一部だけ採用）

MQTTの正式な産業IoT向け規約であるSparkplug Bをそのまま採用するのは今回の規模では大掛かりすぎる
ため、フル準拠はせずに**トピック構造**と**seq番号による欠落検知**の2点だけを取り入れています。

### トピック構造：宛先/報告元の名前をトピックに含める

`OFFER`・`ACK`・`RECEIVED`・`presence`・`JOB完了報告`は、すべて`<種別のトピック>/<関係する名前>`
という形にしています（`JOB`本体だけは全マイコン向けの一斉配信なので例外的に宛先を持ちません）。

| トピック | 名前の意味 | このプロジェクトでの役目 |
|---|---|---|
| `<topic>/file/offer/<宛先名>` | ファイルを受け取る側 | 自分宛てのものだけ購読して受け取る |
| `<topic>/file/ack/<申し出た人の名前>` | 申し出た（送信する）側 | 自分が受け取ったOFFERへの返事として送信する |
| `<topic>/file/received/<マイコン名>` | 受信結果を報告するマイコン | 自分の受信結果を送信する |
| `<topic>/presence/<名前>` | 在室確認するマイコン | 自分のオンライン状態を送信する |
| `<topic>/job/done/<マイコン名>` | ジョブ完了を報告するマイコン | 自分の完了報告を送信する |

自分宛てのトピック（`<topic>/file/offer/<自分の名前>`）だけを購読すればよいので、無関係な
パソコン役からのOFFERをペイロードの中身を見てから捨てる、という無駄がありません。

### seq番号：メッセージの欠落検知

各メッセージには`seq`（連番）フィールドがあり、送信側は自分がpublishするたびに1つずつ増やします。
受信側は前回見た値と比べて1つも増えていなければ、「間の1通が抜けたかもしれない」と警告を表示します
（`seq.rs`の`check_seq`関数）。

**重要な注意点**: seqカウンタは**メッセージの種類（OFFER/ACK/RECEIVED/presence/JOB/DONE）ごとに別々**
に用意しています（`DeviceSeqState`構造体）。理由は、例えば`ACK`は申し出てきた本人だけに届く専用
トピックなので、他の観測者にはそもそも見えないメッセージだからです。もし全種類で1つの共有カウンタを
使うと、ACKの分だけ他の観測者から見て番号が「飛んで」見えてしまい、実際は何も欠落していないのに
誤って警告が出てしまいます（実装中に実際にこの誤検知を確認し、種類ごとのカウンタに直しました）。

このプロジェクト（マイコン役）は「OFFER・JOBを受け取る側」「ACK・RECEIVED・presence・DONEを送る側」
という非対称な役割なので、`DeviceSeqState`にはその組み合わせ分のカウンタ/トラッカーしか持たせて
いません（送る側の"OFFER"や受け取る側の"ACK"などは`mqtt-server`側の`ControllerSeqState`が担当）。

presenceの`"online"`（Sparkplug BでいうBIRTH相当）を受け取ったときだけは、再接続でseqが0から
数え直されるのが正常な動きなので、警告を出さずにカウンタをリセットする扱いにしています。

## MQTTペイロードの形式（JSON）

チャット本文（`<名前>: <内容>`という自由なテキスト）を除く、`OFFER`・`ACK`・`RECEIVED`・`presence`・
`JOB`・`DONE`のような構造化されたメッセージは、すべて`serde`/`serde_json`を使って**JSON形式**で
やり取りしています（`messages.rs`参照）。JSONなら各フィールドに名前が付くので、後方互換を保ちながら
項目を追加しやすく、`mosquitto_sub`などで覗いたときも人間に読みやすいです。

なお、生TCPで送るファイル本体（`file_transfer.rs`）は今まで通りバイナリの長さプレフィックス形式の
ままです。ファイルの生バイトをJSONに埋め込むと単純に非効率（Base64化でサイズが約1.33倍に膨らむ）
なので、そこは意図的にJSON化していません。

## MQTTの仕様と、それを使ってできること

起動時に指定する `<名前>` や `topic` は、このサンプル独自のものではなく、MQTTプロトコル自体が定義している概念です。
これらを理解すると、単純な1トピックのチャット以外にも色々な使い方に応用できます。

### クライアントID（`<名前>`）

MQTT接続時に必須のID。ブローカーはこれで各クライアントを識別します。
**同じIDで同時に2つ接続すると、後から接続した方が優先され先勝ちの接続が切断される**という仕様があるため、
複数端末で試すときは必ず別々の名前を付けてください（このサンプルでは `<名前>` がそのままクライアントIDになります）。

### トピック（`topic`）

`chat` のような文字列で、パブリッシュ（送信）とサブスクライブ（受信）を結びつけるための「宛先」です。
`/` 区切りで階層構造にできるのがMQTTの特徴で、例えば以下のように設計を分けられます。

- `chat/room1`, `chat/room2` … ルームごとに分ける
- `chat/tokyo/alice` … 地域やユーザー単位で分ける
- `sensor/livingroom/temperature` … IoTセンサーのデータ配信

### ワイルドカード購読（`+` と `#`）

サブスクライブ時だけ使える特殊な記号で、複数トピックをまとめて購読できます。

- `+`：1階層だけにマッチ。例: `chat/+` は `chat/room1` や `chat/room2` にマッチ（`chat/room1/x` にはマッチしない）
- `#`：それ以降の全階層にマッチ（末尾にのみ指定可）。例: `chat/#` は `chat/room1` も `chat/room1/sub` も全部拾う

`mqtt-server`側は`<topic>/file/received/+`や`<topic>/presence/+`のように、全マイコン分をまとめて
観測するのにこのワイルドカードを使っています。

### QoS（配信保証レベル）

MQTTには QoS0（最大1回・送りっぱなし）/ QoS1（最低1回・重複あり得る）/ QoS2（正確に1回）の3段階があります。
確実に届けたい用途ならQoS1/2に、多少落ちてもいい大量データ（センサー値など）ならQoS0に、と使い分けます。

### この構成を応用してできること

- **マルチルームチャット**: `topic` をルーム名込みにして、ユーザーにルームを選ばせる
- **在室通知（プレゼンス）**: MQTTの Last Will（接続時に登録し、切断時にブローカーが自動publishしてくれるメッセージ）を使って `presence/<名前>` に online/offline を流す
- **retainフラグの活用**: publish時に `retain=true` にすると、ブローカーがそのトピックの最新メッセージを保持し、後から接続したクライアントにも即座に配信される。「最新のお知らせ」や「現在のステータス」の配信に向いている
- **センサーデータの配信**: chatに限らず、`sensor/...` のようなトピックに数値を流せば、そのままIoTのpub/subにも応用できる

いずれもコード側は `topic` の文字列や `QoS`・`retain` の指定を変えるだけで試せます。
