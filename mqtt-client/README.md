# mqtt-client

[`rumqttc`](https://crates.io/crates/rumqttc) を使った、単体で動くMQTTチャットクライアントです。
`mqtt-server` プロジェクトとは独立しており、単独でビルド・実行できます（接続先のMQTTブローカーは別途必要です）。

## 使い方

```sh
cargo run -- <名前> [host] [port] [topic]

# 例
cargo run -- alice 127.0.0.1 1883 chat
cargo run -- bob   127.0.0.1 1883 chat
```

`host`・`port`・`topic` は省略可能で、それぞれ `127.0.0.1` / `1883` / `chat` がデフォルトです。

起動後、行を入力して Enter を押すと `<名前>: <入力内容>` が指定トピックに publish され、
同じトピックを subscribe している全クライアント（自分自身も含む）に配信されて表示されます。
`Ctrl+D` で送信スレッドを終了できます。

入力行の先頭に `/qos0 ` `/qos1 ` `/qos2 ` を付けると、そのメッセージだけQoSを指定して送信できます（プレフィックスは送信内容から取り除かれます）。省略した場合はQoS1（AtLeastOnce）です。

```
> /qos0 落ちてもいいセンサー値
> /qos2 確実に届けたい重要メッセージ
```

同じホスト上でMQTTブローカーを動かしたい場合は、`mqtt-server` プロジェクトを使ってください。

## ファイル送信（MQTT + 生TCP、パソコン役／マイコン役）

チャット中に以下のように入力すると、ファイルを送信できます。

```
/send <宛先の名前> <ファイルパス>

# 例
/send device1 ./photo.png
```

MQTTは大きなバイナリデータの配信には向いていないため、**ファイルの中身そのものはMQTTに乗せず、
別途つないだ生のTCPソケットで直接送受信**する方式にしています。

さらに、起動時の5番目の引数 `listen_port` の有無で、クライアントの役割を2種類に分けられます。

```sh
cargo run -- pc1     127.0.0.1 1883 chat        # パソコン役: listenしない（指示を出す・ファイルを送る側）
cargo run -- device1 127.0.0.1 1883 chat 9100   # マイコン役: 起動時から9100番ポートで常時listen
```

- **パソコン役**（`listen_port` を省略）: 一切TCPの待ち受け(listen)をしません。ファイルを送ることはできますが、
  受け取ることはできません。社内PCのようにファイアウォールで外からの接続(インバウンド)を塞がれがちな環境でも、
  自分から接続しに行くだけ（アウトバウンド）なので問題になりません。
- **マイコン役**（`listen_port` を指定）: 起動と同時に、そのポート番号で待ち受けを開始し、プログラムが終わるまで
  ずっと待ち続けます（何度でも・複数の相手からでも受信可能）。ファイアウォールの穴あけが必要なのはこの役割の
  クライアントだけなので、開けておくポートを固定・限定できます。

流れは次の通りです。

1. 送信側（パソコン役）が `<topic>/file/offer` トピックへ「このファイルを送りたい」という申し出（ファイル名・サイズ・宛先名など）をpublish
2. 宛先の名前と一致する、かつ`listen_port`を指定して起動している（＝マイコン役の）クライアントだけがそれに反応する。
   すでに起動時からlistenを続けているので、新たに待ち受けを開始する必要はない
3. 「ここに繋いで」という返事（自分の現在のIPアドレス＋固定ポート番号）を `<topic>/file/ack` トピックへpublish
   （IPアドレスはDHCPで変わることがあるため、返事のたびに毎回調べ直しています）
4. 送信側がそのアドレスへ直接TCP接続し、`id`＋ファイル名＋サイズ＋中身の順に流し込む
5. マイコン側は受信が終わった（または途中で失敗した）ら、結果を `<topic>/file/received` トピックへ
   `RECEIVED|id|マイコン名|OK or FAILED|受信できたバイト数` としてpublishする

宛先がパソコン役（`listen_port`未指定）だった場合は待ち受けができないため、オファーを受け取っても
「受け取れません」という警告を表示するだけでACKを返しません（送信側はACKが来ないまま待ち続けます）。

つまりMQTTは「送るよ」「ここで待ってるよ」「届いたよ（または失敗したよ）」という**信号のやり取り
（シグナリング）**にだけ使い、実データの転送は普通のTCPソケット通信で行っています。自分のIPアドレスは
「ブローカーに疑似接続してみて使われるローカルアドレスを覗く」という方法で自動検出しています（同一LAN内
での利用を想定した簡易実装で、インターネット越しやNAT環境ではそのままでは動きません）。

`<topic>/file/received` はパソコン役自身も購読しているので、送信結果をその場の画面でも確認できますが、
**MQTTだけを見ている別の監視ツールやログ収集からも「実際に届いたかどうか」が分かる**のがポイントです。
生TCPでやり取りしているファイルの中身自体はMQTT上には一切現れませんが、その転送結果（成功/失敗）だけは
必ずMQTT側に反映される、という設計にしています。

## ジョブの一斉配信（印刷ジョブキューなど、`/job`）

「今オンラインになっている全マイコンへジョブを配り、全員の完了報告が揃うまで待ってから次のジョブを送る」
という直列実行を行うコマンドです（印刷ジョブキューのような用途を想定）。

```
/job <内容>

# 例
/job print A4x3
```

- **マイコン役の在室確認（presence）**: マイコン役（`listen_port`指定あり）は、接続できたらすぐ
  `<topic>/presence/<名前>` へ`retain=true`で`"online"`をpublishします。さらに接続時にLast Will
  （異常切断時にブローカーが代わりにpublishしてくれる遺言メッセージ）として、同じトピックへの
  `"offline"`を登録しておきます。これにより、正常終了はもちろん、電源断や通信断で「さようなら」を
  言えずに落ちた場合でも自動的に`"offline"`が配信され、ジョブの配信先から自動的に除外されます。
- パソコン役はこの`<topic>/presence/+`（ワイルドカード購読）を見て、**今どのマイコンがオンラインか**
  を動的な名簿として持っています。固定の名前リストを設定ファイルに書いたりする必要はありません。
- `/job`を実行すると、その時点の名簿に載っている全マイコンへ`<topic>/job/queue`にジョブをpublishし、
  各マイコンからの完了報告（`<topic>/job/done`）が**全員分揃うまで、その場で入力をブロックして待ちます**。
  全員完了したら次の`/job`を受け付けられるようになります。
- 一定時間（デフォルト10秒、`main.rs`の`JOB_TIMEOUT`）応答が無いマイコンがいた場合は、
  そのマイコン名を挙げてエラー表示します。

マイコン役は、ジョブを受け取ると（このサンプルでは実際の印刷は行わず）1秒待ってから完了報告を返す、
という簡易的な処理をします。実機では、この「1秒待つ」部分を実際の印刷やモーター制御などの処理に
置き換えることになります。

## MQTTの仕様と、それを使ってできること

起動時に指定する `<名前>` や `topic` は、このサンプル独自のものではなく、MQTTプロトコル自体が定義している概念です。
これらを理解すると、単純な1トピックのチャット以外にも色々な使い方に応用できます。

### クライアントID（`<名前>`）

MQTT接続時に必須のID。ブローカーはこれで各クライアントを識別します。
**同じIDで同時に2つ接続すると、後から接続した方が優先され先勝ちの接続が切断される**という仕様があるため、
複数端末で試すときは必ず別々の名前を付けてください（このサンプルでは `<名前>` がそのままクライアントIDになります）。

### トピック（`topic`）

`chat` のような文字列で、パブリッシュ（送信）とサブスクライブ（受信）を結びつけるための「宛先」です。
`/` 区切りで階層構造にできるのがMQTTの特徴で、例えば以下のように設計を分けられます。

- `chat/room1`, `chat/room2` … ルームごとに分ける
- `chat/tokyo/alice` … 地域やユーザー単位で分ける
- `sensor/livingroom/temperature` … IoTセンサーのデータ配信

### ワイルドカード購読（`+` と `#`）

サブスクライブ時だけ使える特殊な記号で、複数トピックをまとめて購読できます。今のクライアントは
指定した1トピックをそのままsubscribeするだけなので、`topic` 引数に直接ワイルドカードを渡せば動きます。

- `+`：1階層だけにマッチ。例: `chat/+` は `chat/room1` や `chat/room2` にマッチ（`chat/room1/x` にはマッチしない）
- `#`：それ以降の全階層にマッチ（末尾にのみ指定可）。例: `chat/#` は `chat/room1` も `chat/room1/sub` も全部拾う

→ **応用例**: `mqtt-client alice 127.0.0.1 1883 chat/#` と起動すれば、`chat/`配下の全ルームのメッセージを1クライアントで監視できます（ロギングや管理用の「見張り役」クライアントが作れる）。

### QoS（配信保証レベル）

MQTTには QoS0（最大1回・送りっぱなし）/ QoS1（最低1回・重複あり得る）/ QoS2（正確に1回）の3段階があります。
このサンプルではsubscribeはQoS0固定ですが、publishは`/qos0` `/qos1` `/qos2`プレフィックスでメッセージごとに切り替えられます（上記の「使い方」参照）。
確実に届けたい用途ならQoS1/2に、多少落ちてもいい大量データ（センサー値など）ならQoS0に、と使い分けます。

### この構成を応用してできること

- **マルチルームチャット**: `topic` をルーム名込みにして、ユーザーにルームを選ばせる
- **在室通知（プレゼンス）**: MQTTの Last Will（接続時に登録し、切断時にブローカーが自動publishしてくれるメッセージ）を使って `presence/<名前>` に online/offline を流す
- **1対1のダイレクトメッセージ**: `dm/<宛先>/<送信者>` のようなトピック設計にして、宛先トピックだけをsubscribeさせる
- **retainフラグの活用**: publish時に `retain=true` にすると、ブローカーがそのトピックの最新メッセージを保持し、後から接続したクライアントにも即座に配信される（今回は `false` 固定）。「最新のお知らせ」や「現在のステータス」の配信に向いている
- **センサーデータの配信**: chatに限らず、`sensor/...` のようなトピックに数値を流せば、そのままIoTのpub/subにも応用できる

いずれもコード側は `topic` の文字列や `QoS`・`retain` の指定を変えるだけで試せます。
